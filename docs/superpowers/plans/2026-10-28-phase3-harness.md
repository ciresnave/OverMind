# Phase 3: Harness and Plug-in API Plan

> **Status: a plan, written 2026-10-28 against `origin/main` `3c14339`; nothing here is built.** CireSnave ruled
> 2026-10-25 *"A3: Build the harness/plug-in API."* (relayed by the PM, who recorded it as overriding the earlier
> "defer"). Spec: `ARCHITECTURE-LAYERS-SPEC.md` sections 1-3 and 9 Phase 3 (approved 2026-10-08, board 143).
> Policy: `DESIGN-PROPOSAL.md` section 7.5 (CireSnave 2026-10-28). Every PR below is its own PR, red-first,
> reviewed by a separate Sonnet subagent with its checklist written first, and gated and merged by the PM.

**Goal:** the spec's guarantee, built: every model output and every tool call passes a plug-in pipeline, a plug-in
cannot act around it, and the orchestrator reads back what loaded.

**Scope limits.** The spec's own honest limit stands: in-process Python stops accidental bypass, not a hostile
plug-in. Phase 4 (the handler) and 5 (routing) are not here.

## Facts this plan rests on (read at `3c14339`)

- The loop is `run_agent` (`agent.py`); the one path from a model tool call to an effect is
  `GatedExecutor.execute` (`gate.py:593`), whose decision is `Gate.decide` (`gate.py:517`): only policies that
  apply are asked, the first denial returns, a call no policy applies to is denied. `Policy.applies_to` and
  `Policy.decide(call, facts)` are the existing hook shape for `before_tool_call`.
- `tests/test_import_direction.py` freezes the import edges; every new module needs its edges added **on purpose**.
- `lanework.run_task` wires gate, executor and `run_agent` by hand, then runs the check itself.
- Python audit hooks cannot be removed (spec section 3, measured on 3.14.7). P3.3 re-measures that on the
  interpreter CI runs before relying on it.
- **Unmeasured, to measure in P3.3 (the spec's own ASSUMED lines):** that the harness can mark all its own I/O
  (third-party libraries included) as harness-owned without false stops; that the audit events named cover the
  fixtures.

## The PRs, in order

Each PR leaves `main` green and changes no behaviour of a path it does not name.

| PR | What | Tests first (seen red) | Does not touch |
|---|---|---|---|
| **P3.1 data** | `src/overmind/harness/config.py`: `SessionConfig` (schema_version 1, fields per spec section 2) and `LoadedManifest`; JSON load that **refuses** an unknown `schema_version`, an unknown field and wrong types (`Task._check_types` style: a `bool` is not an `int`). `manifest.py`: SHA-256 of a plug-in's source file, and `compare(config, manifest)` returning every difference | refuse unknown version; refuse a partial config; the manifest differs from the config in each field; the hash changes with one byte | `agent.py`, `gate.py`, `lanework.py` |
| **P3.2 pipeline** | `src/overmind/harness/plugin_api.py`: the hooks of spec section 2 with their result types (`Ok/Refuse`, `Pass/Rewrite/Drop`, `Allow/Deny`, ...), **no result means "proceed anyway"**; `declares()`; the `api_version` major check, which refuses a mismatching plug-in and never runs a partial pipeline. `src/overmind/harness/pipeline.py`: runs plug-ins in config order; `before_tool_call` keeps `Gate.decide` semantics exactly (`gate.py:517-553`): only policies that apply are asked, the first denial returns, nothing applying means deny, **and the fourth rule: a policy with `requires_vouched_sender` refuses with the `unvouched-sender` decision unless the `sender_vouched` fact is exactly `True`**, and success returns the last allow. Per-thread `allowed_call` and `primitive_frame` (`threading.local`); **effect primitives** that raise when `allowed_call` is clear. Adapter: today's `Gate` as the first plug-in, with the same decisions | the existing `tests/test_gate.py` cases run through the pipeline and give identical `Decision`s (they include the unvouched-sender refusal, `test_gate.py:448`, and a missing vouch fact, `:456`); a primitive refuses with `allowed_call` clear; `allowed_call` is cleared while any hook runs, `after_tool_call` included; a new thread starts with neither frame | `run_agent` still calls `GatedExecutor` |
| **P3.2b process per session** | `spawn(config)` starts one harness process per session (spec section 1 and section 3, item 2); `handle.loaded()`, `.events()`, `.stop()`. Lands **before** P3.3, which arms the audit hook only in the child processes this PR starts | a session's audit hook state never leaks to its parent; `loaded()` reads the manifest from the child | `lanework` callers other than the orchestrator recipe |
| **P3.3 chokepoint** | the static scan test (spec section 3, tests item 1), the audit hook armed first in the session process and never disarmed (item 2), **armed only in a child process started for that session or test, never in pytest's or the orchestrator's own process** (a hook that cannot be removed would otherwise outlive the test and flag every later test; the one-process-per-session PR, P3.2b, therefore comes **before** this one and supplies the child process the tests arm in), the rogue fixtures each caught by **exactly one** layer, and the mutation tests (item 4). **First action: measure** the two ASSUMED lines above and the interpreter's audit-hook facts; if either fails, stop and report | one fixture per layer naming its expected event or refusal; each mutation turns its named test red (audit hook off; scan removed; primitive refusal removed; hooks not clearing `allowed_call`; armed flag in a `contextvar`) | any existing plug-in |
| **P3.4 plug-ins** | `ledger`, `workspace-tools`, `fork` and MCP become plug-ins, one PR each; `run_agent` drives the pipeline instead of `GatedExecutor`. `lanework._run` and `lanework._git` become the first effect primitives, carried by `workspace-tools`. A fork's child pipeline is built from the parent's loaded plug-ins (spec section 3, item 2) and loads none | for each move: that piece's existing tests unchanged and green, plus the fork fixture; `ForbidTools(fork)` still holds | the handler (Phase 4) |
| **P3.5 task policy** | a `check-policy` plug-in implementing `DESIGN-PROPOSAL.md` section 7.5 at `on_session_start`. **How provenance is carried is a design decision made here (proposal, the PM's to overrule):** `Task.check` is a plain `list[str]` (`lanework.py:129`) and `check_name` is a label, so a registry-derived argv and a caller-supplied one are the same value, and `Task` has no `check_profile` field today (it lives on the dispatch request, `dispatch_mcp.py:161`). This PR therefore adds two `Task` fields, both set only by the orchestrator code that builds the `Task`, never read from a dispatch message: `check_profile: str | None` (what `dispatch_mcp` already received) and `trusted_author: bool = False` (set only by the CLI entry for a hand-run `task.json`, the unchanged trust boundary of 7.5). The policy re-derives: it accepts a `Task` only if `Task.check` **equals** `infer_check(worktree, task.check_profile).check` (a `CheckResult` whose `.check` is `None` when it refused: `None` means refuse), **or** equals `DOCS_ONLY_CHECK` (`dispatch_mcp.py:211`, CireSnave's ruling recorded in 7.4), **or** `trusted_author` is true. Anything else is refused. The spec's sample `SessionConfig` has a `check` plug-in with an `argv` in its config: that form is accepted only under `trusted_author`. **Also assess and record** whether each `CHECK_TABLE` / `NAMED_CHECK_PROFILES` entry should additionally be sandboxed (they run repo code, including what the model just wrote; the rule allows pre-defined commands on the host, so this is a question for the PM, not a precondition). The sandbox half is P3.7; this PR ships only the refusal | a `Task` with a caller-supplied argv (even one equal to a registry argv for a different repo) is refused; `infer_check(...).check` is accepted, and a `None` result with a non-empty `Task.check` is refused; `DOCS_ONLY_CHECK` is accepted; `trusted_author` is accepted and only the CLI sets it (a dispatch-built `Task` cannot); an unknown profile name is refused; mutation: delete the policy and the refusal test turns red | `dispatch.py` stays unconnected (`dispatch_mcp.py` already calls `run_task`, so P3.5 changes its behaviour only for a non-registry check, which it cannot build today) |
| **P3.6 orchestrator** | `lanework` writes a `SessionConfig` and compares the `LoadedManifest` before the first turn; any difference stops the session | a config/manifest mismatch stops before turn 1 (a fake harness) | nothing else |
| **P3.7 sandbox seam** | `DESIGN-PROPOSAL.md` 7.5's agent-generated half, against AntSpawn as it is (`origin/main` `0325da0`, `windows-sandbox` and `account` launchers certified for the isolation set): translate a dispatch-supplied check into an AntSpawn job spec (read-only checkout mount, declared outputs, `network = "off"`, limits), run it through `spawn run`, refuse when no certified launcher exists. **First action: read AntSpawn at its then-current `origin/main` and measure** what a Python or Cargo check costs in a `windows-sandbox` VM (start latency, toolchain load, the Smart App Control one-start limit on unsigned exes), because that is unmeasured | a spec that asks for the network is refused; a check that writes outside its declared output leaves nothing on the host (known-bad control: the same command on the host does write); no certified launcher means refusal, not a host run; mutation: route the check to the host path and the isolation test turns red | `dispatch.py` stays unconnected until this lands and the PM schedules wiring |
